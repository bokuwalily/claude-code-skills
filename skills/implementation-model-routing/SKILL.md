# 実装タスクのモデル自動振り分け

コードを書くタスクを受けたら、頼まれなくてもこの基準で自分で振り分ける。
目的＝品質を落とさずコストだけ下げる。劣化は「Sonnetに判断をさせたとき」だけ起きる。

**運用方針（v2）＝委譲をデフォルトにする。** メインはOpus固定で動いているので、能動的に委譲しないとSonnetは一切使われずコストが落ちない。だから旧版の「迷ったらOpus」は捨て、**「定型はためらわず必ずSonnet委譲」**で回す。委譲判断はTodoWriteに明示して取りこぼしを防ぐ。

## Procedure

0. **着手の最初のTodoで必ず振り分けを宣言する（強制ゲート）。** コードを書くタスクに入ったら、最初のtodo項目に `モデル振り分け: <判断あり=Opus自実装 / 定型=Sonnet委譲>` を必ず入れてから実装に入る。このtodoを立てないまま実装を書き始めない＝発火の取りこぼしをここで止める。1タスク内に定型サブタスクが混ざるなら、その単位で個別にtodo化して委譲する。

1. **タスクを「判断を含むか」で分類する**（着手前に必ず）。デフォルトは委譲。「Opusで書く」を選ぶには下記2の該当理由を1つ言えること（言えないなら定型＝委譲）。

2. **判断を含む → 自分(Opus)で直接実装する。委譲しない。** 該当:
   - アーキテクチャ・モジュール境界・データモデル設計
   - 難しいアルゴリズム / 並行性・非同期・状態設計
   - API契約・エラー設計・境界値・後方互換の解釈
   - 仕様が曖昧で意図の補完が要るもの
   - セキュリティ・認可・課金・マイグレーションなど壊れると痛い箇所

3. **判断を含まない定型作業 → 委譲する。** 該当:
   - 決まった形のCRUD・ボイラープレート・設定ファイル
   - テスト生成（仕様が固まっているもの）
   - 機械的リファクタ・リネーム・型合わせ・import整理
   - 既存パターンの横展開・別言語/別FWへの移植
   - 単純なバグ修正（原因と直し方が確定しているもの）

   委譲先の優先順位:
   - **①大規模・反復・独立した実装（指示を文章で固め切れる）→ Codex優先**（`codex exec`、ChatGPT Pro枠でClaudeトークンを節約するのが主目的）。**必ず空振り防止の型で投げる＝**（作業dir絶対パス＋@file全列挙＋出力先＋完了条件＋検証コマンドを1指示文に固める→投げ後 `git diff --stat` で実変更を確認）。
   - **②私の調査結果・設計判断と密に往復が要る／対象ファイルが散在して文脈共有が重い → `Agent(model:"sonnet")`**（同セッション統合でファイル文脈を引き継げる）。
   - Codexが2回空振り（timeout/空出力/別dir書込み/的外れ）したら①→②へフォールバック。

4. **委譲するときは意図を口頭でなく明文化して渡す**＝型・インターフェース・制約・参照すべき既存パターン・期待する入出力。Sonnetは「決まったものを実装」は得意、「曖昧な意図の補完」は苦手。

5. **委譲後は必ず自分(Opus)でレビューする。** 設計Opus→実装Sonnet→レビューOpus の三段が最も品質が出る。レビュー省略禁止。

6. 純粋に機械的・低リスク（一括置換、定型スクリプト雛形等）は `haiku` サブエージェントでも可。

## 発火の実体（重要）

- このスキルは **フック `~/.claude/hooks/model_routing_reminder.sh`（UserPromptSubmitに登録）** で強制発火する。プロンプトをgrepし実装タスク検知時にこの要約をcontext注入する。
- ⚠️auto/配下のスキルは `~/.claude/skills/auto/<名>/SKILL.md` と1階層深く、**Skillツールのフラット走査(`~/.claude/skills/<名>/SKILL.md`)に載らない＝呼び出し不可・自動発火しない**。だから「skillファイルを置くだけ」では効かず、フック注入で強制している（2026-06-22に判明・修正）。

## Pitfalls

- **「委譲が面倒だから全部Opusで書く」が最大の失敗。** これがv1で起きた劣化＝Sonnet使用量が落ちなかった原因。定型と分かったら必ず委譲する。サブエージェント起動の一手間を惜しまない。
- **ただし判断が混ざる実装をSonnetに丸投げもしない。** 境界の見誤りは別方向の劣化。分類2に該当理由が言えるものだけOpusで書く（「なんとなく不安」はOpus行きの理由にならない＝制約を明文化して委譲する）。
- 意図を型・制約で渡さず口頭レベルで委譲すると劣化する。型・インターフェース・参照パターンを必ず添える。
- レビューを省略しない（速くなったぶんをレビューに回す）。設計Opus→実装Sonnet→レビューOpusの三段を守る。
- 手動で明示的に判断材料が欲しいときは `/model-route` コマンドを使う（このスキルはその自動発火版）。

## Verification

- 委譲した実装がインターフェース契約・制約を満たしているか自分で確認
- テストが緑か実行して確認
- 判断を含む箇所をSonnetに渡していないか、着手分類を見直す
